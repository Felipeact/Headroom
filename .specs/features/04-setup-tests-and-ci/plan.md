# 04 - Tests and CI

## Problem

Nothing checks a change before it lands. The checks in `AGENTS.md` ("Before you finish a task") run only when whoever made the change remembers to run them, on their own machine. `development` deploys to staging (spec 05) and `main` to production, and neither branch is protected (`gh api .../branches/main/protection` answers `404 Branch not protected`; no rulesets exist). The frontend half of that checklist can't even be run yet: `package.json` has no `typecheck` or `test` script, and there is no Vitest or Playwright. Every screen spec from 06 onward needs those, because `AGENTS.md` requires a Vitest component test and a Playwright test with an axe check for every screen. Dependabot alerts are off (`vulnerability-alerts` answers `404`), so a vulnerable dependency in an app that handles bank data goes unreported.

When this ships, every pull request into `development` or `main` runs a `web` job and an `api` job on GitHub Actions, the pull request can't be merged until both pass, and a type error turns the run red. The source gives no evidence beyond the roadmap's build order.

## Flow

This reuses the checks `AGENTS.md` already lists, spec 03's tests, its `DATABASE_URL` settings contract (AD-001) and the `postgres:17` image from `docker-compose.yml`. Vitest and Playwright are created by their official setup steps, not written by hand.

1. a pull request into `development` or `main`, or a push to `development` -> `.github/workflows/ci.yml` (door 1) starts two independent jobs
2. job `web` -> `frontend/` (exists): `npm ci`, `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`
3. job `api` -> `services/core/` (exists): `astral-sh/setup-uv` installs uv; a `postgres:17` service container starts; `DATABASE_URL` points at it; `uv run ruff format --check .`, `uv run ruff check .`, `uv run mypy app`, `uv run pytest`
4. out: two check runs named `web` and `api` on the pull request's head commit, which branch protection on `development` and `main` requires (door 1)

## Impact

| Front | What changes |
| --- | --- |
| frontend scripts | new `typecheck`, `test` and `test:e2e` scripts. `npm test` now has to exit on its own, because both CI and the AGENTS.md checklist run it |
| frontend dependencies | new dev dependencies from the Next.js Vitest guide (`vitest`, `@vitejs/plugin-react`, `jsdom`, `@testing-library/react`, `@testing-library/dom`, `vite-tsconfig-paths`) and from `npm init playwright@latest` (`@playwright/test`); `package-lock.json` is regenerated by npm |
| test discovery | Vitest's default pattern matches `*.spec.ts`, which is also Playwright's file name. Without an exclusion, `npm test` would try to run the Playwright tests |
| merging | once protection is on, a pull request into `development` or `main` can't be merged until `web` and `api` pass. Admin bypass stays on, so the owner can still push commits straight to `development` as `AGENTS.md` describes (see Assumptions) |
| repository settings | Dependabot alerts turn on; branch protection on `development` and `main`. These are GitHub settings, not files, so they are applied with `gh api` and checked with `gh api` |
| AGENTS.md | none. Its check commands become runnable as written |
| stored data | nothing |

## Criteria

### S1: The frontend checks run locally (P1)

A developer, or the `web` job, can run every frontend check with one command each.

**Acceptance Criteria**

1. WHEN `npm run typecheck` runs in `frontend/` THEN it SHALL run `tsc --noEmit` and exit 0 on the current code
2. IF a `.ts` or `.tsx` file under `frontend/` contains a type error THEN `npm run typecheck` SHALL exit non-zero
3. WHEN `npm test` runs in `frontend/` THEN Vitest SHALL run every `*.test.ts(x)` file once in `jsdom` and exit, without watching for changes, and SHALL exit 0 with at least one passing component test that renders `app/page.tsx` with Testing Library
4. WHEN `npm test` runs THEN it SHALL run no file under `frontend/e2e/`
5. WHEN `npm run test:e2e` runs in `frontend/` THEN Playwright SHALL start the app on `localhost:3000` itself, run the tests in `frontend/e2e/`, and exit 0 with at least one passing test that loads `/`
6. WHEN `npm run lint` and `npm run build` run in `frontend/` THEN both SHALL still exit 0

**Independent test:** in `frontend/`: `npm ci && npm run lint && npm run typecheck && npm test && npm run build && npm run test:e2e`, all exit 0.

### S2: CI runs both jobs on every pull request (P1)

GitHub runs the same checks on every pull request into `development` or `main`.

**Acceptance Criteria**

7. WHEN a pull request into `development` or `main` is opened or updated, or a commit is pushed to `development`, THEN GitHub Actions SHALL run the workflow `CI` with two jobs, `web` and `api`
8. WHEN the `web` job runs THEN it SHALL run, in `frontend/`, `npm ci`, `npm run lint`, `npm run typecheck`, `npm test` and `npm run build`, and SHALL fail if any of them exits non-zero
9. WHEN the `api` job runs THEN it SHALL install uv with `astral-sh/setup-uv` and run, in `services/core/`, `uv run ruff format --check .`, `uv run ruff check .`, `uv run mypy app` and `uv run pytest`, and SHALL fail if any of them exits non-zero
10. WHILE the `api` job runs, a `postgres:17` service container SHALL be reachable at the `DATABASE_URL` the job sets, so spec 03's database tests run in CI instead of being skipped
11. WHEN a pull request into `development` contains no errors THEN both `web` and `api` SHALL show as passed on it
12. IF a pull request adds a deliberate type error to a `.tsx` file under `frontend/` THEN the `web` job SHALL fail at `npm run typecheck`, and the workflow run SHALL show as failed
13. The workflow SHALL use no repository secrets; the only credentials in it are the throwaway CI Postgres user and password, which match `docker-compose.yml`

### S3: The repository enforces it (P1)

GitHub refuses to merge a red pull request and reports vulnerable dependencies.

**Acceptance Criteria**

14. WHEN branch protection on `development` and on `main` is read with `gh api` THEN each SHALL list `web` and `api` as required status checks
15. IF a pull request into `development` has a failed `web` or `api` check THEN GitHub SHALL report it as not mergeable (`mergeStateStatus` `BLOCKED`)
16. WHEN `gh api repos/Felipeact/Headroom/vulnerability-alerts` is called THEN it SHALL answer `204` (alerts on)

**Independent test:** open a throwaway pull request into `development`: both checks go green. Push a type error to it: `web` goes red and the pull request shows as blocked. Close it and delete the branch.

## Assumptions

| Assumption | Chosen default | Rationale | Confirmed? |
| --- | --- | --- | --- |
| How strict protection on `development` is | require `web` and `api` on pull requests into `development` and `main`; don't require a pull request, and leave "include administrators" off | `AGENTS.md` says every spec is built on `development` and commits go there directly. Enforcing for admins would reject those pushes. Protection still blocks red pull requests from anyone else | y |
| How the Done-when items are proven | push `development` once the work is committed; then a throwaway branch `ci/spec-04-proof` and a pull request into `development`: first green, then with a type error added, then closed and the branch deleted | the spec needs a real pull request, and pull requests into `main` happen only for releases. `AGENTS.md` asks first before a new branch, and pushing needs a go-ahead; the user authorized all of these actions on 2026-10-01 | y |
| Plan supports protection on a private repository | yes | `gh api .../branches/main/protection` answered `404 Branch not protected`, not the `403 Upgrade to GitHub Pro` a Free private repository gets. The token has no `user` scope, so the plan name itself couldn't be read | n |
| `ruff format --check` in CI | included in the `api` job | the spec lists `ruff check`, `mypy` and `pytest`; `AGENTS.md`'s checklist also has `ruff format --check`. CI should run the same list the agent runs | n |
| `test` script | `vitest run`, not the guide's `vitest` | plain `vitest` watches when not in CI, so the AGENTS.md checklist would hang locally | n |
| Playwright setup | `npm init playwright@latest` with TypeScript, folder `e2e`, no GitHub Actions workflow, Chromium only; the generated example test (which loads playwright.dev) is replaced with one that loads `/` from the local app through `webServer` | a test that calls a public website is flaky and tests nothing of ours. The exact non-interactive flags are read from `create-playwright`'s source before use | n |
| Python in CI | the version in `services/core/.python-version` (3.12), installed by `setup-uv` | the same version as local development | n |
| Commit split | commit 1: generated Vitest and Playwright setup and the lockfile; commit 2: scripts, configs and tests; commit 3: `ci.yml`. Repository settings are changed after the push | keeps generated files reviewable on their own, as in specs 02 and 03 | n |

**Open questions:** none - the user authorized the push, the throwaway branch and pull request, Dependabot alerts and branch protection with admin bypass (2026-10-01).
