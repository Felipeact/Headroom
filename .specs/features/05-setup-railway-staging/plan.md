# 05 - Staging on Railway

## Problem

Headroom runs only on a developer's machine. Nobody can open the web app or call the API at a shared URL, so a change on `development` is first exercised by a real network, a managed Postgres and a production build only when it reaches production, which is the most expensive place to find a missing variable, a migration that does not apply or a start command that only works locally. Every later spec that depends on the outside world needs a public address before it can be tested at all: Clerk (spec 10) redirects to one, Plaid (specs 12, 14) sends webhooks to one, and the hourly jobs service (spec 15) runs beside the API in the same project. The source gives no evidence beyond the roadmap's build order; it does say staging deploys from `development` and that `main` and production arrive in spec 34.

When this ships, a commit that reaches `development` on GitHub builds and deploys the changed app to a Railway `staging` environment in US East with no manual step: the API runs its migrations before going live and is only promoted once `/healthz/ready` answers `200`, and the web app answers at its own Railway domain.

## Flow

This reuses the existing `/healthz/ready` probe (AD-002) as Railway's health check, the `Settings` contract (AD-001) for `DATABASE_URL`, and the Alembic chain from spec 03 as the pre-deploy step; the builder is Railway's own (Railpack), with no Dockerfile unless it cannot build the API.

1. push to `development` on GitHub -> Railway project `headroom`, environment `staging` (door 1) - matches the changed paths against each service's watch patterns and starts a build only for `api`, `web` or both
2. `api`: Railpack builds `services/core` from `pyproject.toml` + `uv.lock` (no dev group), with the service settings that `railway config apply` wrote from `.railway/railway.ts` (door 4)
3. `api` pre-deploy: `alembic upgrade head` in a separate container on the private network, `DATABASE_URL` from the `Postgres` service (door 3) -> `migrations/env.py` (exists) applies revisions; a non-zero exit stops the deploy
4. `api` start: `fastapi run app/main.py`, which reads `PORT` from the environment -> `app/main.py` (exists); Railway polls `GET /healthz/ready` (exists) until `200`, then routes the `api` public domain to the new deployment
5. `web`: Railpack builds `frontend` (`npm ci`, `npm run build`), with the settings from `.railway/railway.ts` (door 4), starts `next start` on `$PORT`, Railway polls `GET /` until `200`, then routes the `web` public domain to it
6. out: two `*.up.railway.app` domains (`api`, `web`) and the `Postgres` service with no public domain

## Impact

| Front | What changes |
| --- | --- |
| hosting | new Railway project with one environment, `staging`, and three services: `Postgres`, `api`, `web`. `production` is added by spec 34 as a second environment of the same project |
| repository | new folder `.railway/`: `railway.ts` (the service settings), `README.md` (generated by `railway config pull`), and `package.json` + `package-lock.json` pinning the SDK `railway` 3.12.0, a new npm dependency outside `frontend/`. No Dockerfile unless Railpack fails on the API (assumption below). Service settings change only through `railway config apply`; a push deploys code, not settings |
| configuration | staging variables live only in Railway: `DATABASE_URL` on `api`, composed from the `Postgres` service's reference variables. Nothing is added to `.env.example` |
| branch flow | every push to `development` on GitHub now deploys once its GitHub checks pass (`checkSuites`). Today nothing happens on push. `development` already requires the `web` and `api` checks from spec 04 |
| `/healthz/ready` | gains its first consumer outside the code: Railway's deploy health check. Its contract (AD-002) cannot change shape without breaking deploys |
| spec 10 (Clerk) | `/healthz/*` must stay exempt from auth, or every deploy fails its health check (already noted in spec 03's plan) |
| spec 09 / later | when `web` calls `api` server-side over Railway private networking, `api` must listen on IPv6 (`--host ::`); with only public domains today, `fastapi run`'s default host is enough. Not built here |
| stored data | a new, empty staging database; `alembic upgrade head` with no revisions leaves only `alembic_version`. Nothing to migrate |

## Relations

None - no stored-data shape change. The staging database receives exactly the schema the migration chain produces.

## Surface

None - nothing new is consumed outside. The staging domains serve the routes that already exist (`GET /healthz/live`, `GET /healthz/ready`, the web app's `/`); their signatures do not change.

## Criteria

### S1: The API deploys to staging and proves it reaches its database (P1)

Opening the staging API's readiness URL shows that the deployed code, its migrations and its database work together.

**Acceptance Criteria**

1. WHEN a deployment of `api` in `staging` succeeds THEN `GET https://<api staging domain>/healthz/ready` SHALL respond `200` with JSON body exactly `{"status": "ok"}`
2. WHEN a deployment of `api` in `staging` succeeds THEN `GET https://<api staging domain>/healthz/live` SHALL respond `200` with JSON body exactly `{"status": "ok"}`
3. WHEN `api` deploys THEN the deploy log SHALL show `alembic upgrade head` running before the new deployment starts, and afterwards the staging database SHALL contain the table `alembic_version`
4. IF the pre-deploy command `alembic upgrade head` exits non-zero THEN Railway SHALL mark that `api` deployment failed and SHALL NOT route traffic to it
5. IF `GET /healthz/ready` does not return `200` within the health-check timeout THEN Railway SHALL mark that `api` deployment failed and SHALL NOT route traffic to it
6. The `Postgres` service in `staging` SHALL have no public domain or TCP proxy

**Independent test:** in the Railway dashboard, redeploy `api` in `staging`; the deploy log shows the pre-deploy step, the deployment turns Active, and `curl -i https://<api staging domain>/healthz/ready` prints `200` and `{"status":"ok"}`.

### S2: The web app deploys to staging and loads (P1)

Anyone with the link can open the staging web app.

**Acceptance Criteria**

7. WHEN a deployment of `web` in `staging` succeeds THEN `GET https://<web staging domain>/` SHALL respond `200` with an HTML document
8. WHEN `https://<web staging domain>/` opens in Chromium at 375 pixels wide THEN the page SHALL render its `<main>` element with no console error and a document no wider than the viewport

**Independent test:** open the web staging domain in a browser; the start page renders. `curl -i https://<web staging domain>/` prints `200`.

### S3: A push to `development` deploys only what changed (P1)

Merging into `development` is the only step needed to update staging, and an unrelated change does not redeploy the other app.

**Acceptance Criteria**

9. WHEN a commit that changes a file under `services/core/` reaches `development` on GitHub and its `web` and `api` checks succeed THEN Railway SHALL start a new `api` deployment in `staging` for that commit SHA with no manual action
10. WHEN a commit that changes a file under `frontend/` reaches `development` on GitHub and its `web` and `api` checks succeed THEN Railway SHALL start a new `web` deployment in `staging` for that commit SHA with no manual action
11. WHEN a commit that changes no file under `services/core/` reaches `development` THEN Railway SHALL NOT start a new `api` deployment for it
12. WHEN a commit that changes no file under `frontend/` reaches `development` THEN Railway SHALL NOT start a new `web` deployment for it
13. WHEN a commit reaches any branch other than `development` THEN Railway SHALL NOT deploy it to `staging`

**Independent test:** push one commit touching only `frontend/` and one touching only `services/core/`; the `staging` deployment list shows exactly one new `web` deployment and one new `api` deployment, each with the matching SHA.

### S4: No staging secret lives in the repository (P1)

Configuration is in Railway; the repository holds only non-secret build and deploy settings.

**Acceptance Criteria**

14. The file `.railway/railway.ts` SHALL contain no literal credential, host name or `.up.railway.app` domain; its only connection string SHALL be the reference template in door 3
15. The tracked files SHALL include no `.env*` file other than `services/core/.env.example` (repeatable `git ls-files`)
16. The `api` service in `staging` SHALL define `DATABASE_URL` as the reference-variable template in door 3, not as a literal value
17. The services `Postgres`, `api` and `web` in `staging` SHALL each run in Railway's US East region
18. IF the Railway project has an environment other than `staging` (Railway creates `production` with every new project) THEN that environment SHALL have no deployment of `api` or `web`
19. WHEN `railway config plan --detailed-exit-code` runs against `staging` THEN it SHALL exit 0, meaning the live settings equal `.railway/railway.ts`

**Independent test:** `git ls-files | grep -i '\.env'` prints only the example files; the `api` variables tab shows `DATABASE_URL` with `${{Postgres.…}}` references.
