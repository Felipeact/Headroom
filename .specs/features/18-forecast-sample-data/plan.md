# 18 - Sample data

## Problem

Specs 19 to 25 need a business with history to test against: recurring payment detection (19), the 13-week forecast (21), the backtest (22), the cash gap alert (24) and its fixes (25). Today the only bank data comes from the Plaid sandbox, whose transactions are random, change between runs, and show no payroll, rent or cash gap. AGENTS.md forbids copying real customer data anywhere. So each later spec would invent its own data, and their tests would disagree about what the "sample data" is.

The mockups already describe one business, Harbor Street Plumbing, down to the cent. It has two banks, $42,300 of cash, a $2,450 card payment due Oct 8, $20,000 of available credit, and a gap in the week of Nov 9 with a projected low of $3,150. Specs 24 and 25 name that gap and its three fixes ($12,750, $17,650, $5,150) as their "Done when" checks. Nothing in the repository produces it.

There is also no API route that returns transactions, so "available through the API" (spec 18 "Done when" 2) can't be shown today. The user chose to add a read-only route.

When this ships, `app.fixtures.harbor_street.generate(seed)` returns the same Harbor Street Plumbing data every time for a given seed: accounts, 18 months of transactions, the expected payments from the mockup, and a reference 13-week future that holds the Nov 9 gap. `uv run python -m app.fixtures.load harbor_street` loads it into the local database through the real connect and sync path. The owner can then read the accounts and every transaction through the API.

## Flow

The loader reuses spec 11's `accounts.service.get_or_create_user` / `create_business`, spec 12's `bank_sync.service.connect_bank`, spec 13's `update_account`, and spec 14's `sync_connection`. Through them it also gets the one sign flip, the relabelling (spec 16), the audit entries and the `transactions.synced` publish. It writes no table directly. The fixture talks to them as Plaid would, through a `PlaidClient` (AD-036) that serves the fixture.

1. `uv run python -m app.fixtures.load harbor_street [--seed N] [--clerk-user-id ID]` -> `app.fixtures.load` (new, door 3). It refuses a non-local database, then calls `subscriptions.register()` (exists, AD-055).
2. `app.fixtures.harbor_street.generate(seed)` (new, door 2) -> a `SampleBusiness`: business, banks and accounts, history (our sign, integer cents), expected payments, and the reference future. Pure, with no I/O.
3. `accounts.service` (exists) - get or create the owner user, then create the business. If that owner already owns the fully loaded sample, stop: already loaded.
4. For each bank: `bank_sync.service.connect_bank` (exists), given a `FixturePlaidClient` (new, door 3) that serves the bank's accounts and institution. Stores the connection (with an encrypted placeholder token), its accounts and the audit entry.
5. `bank_sync.service.update_account` (exists) - make reserve savings count as cash (a new connection includes only checking, AD-040). Operating checking stays primary.
6. `bank_sync.service.sync_connection(now=2026-09-26T10:02:00Z)` (exists) - the fake serves the history as one Plaid page. Plaid's sign convention is restored for it, and `_values` flips it back. Stores the transactions, relabels the business, commits, and publishes `transactions.synced`.
7. Out: one `fixture.loaded` log line and the business ID on stdout. Then `GET .../bank/connections` (exists) and `GET .../bank/transactions` (new, door 1) read it, owner only.

## Impact

| Front | What changes |
| --- | --- |
| domain | new term: `sample business` - Harbor Street Plumbing, generated by `app.fixtures.harbor_street`. Specs 19, 21, 22, 24, 25 and 26 test against it |
| domain | new term: `reference future` - the fixture's intended next 13 weeks: the flows that specs 21 to 25 must reproduce from the history and the expected payments. It is test data, not a forecast. Nothing in the app reads it |
| API contract | new route `GET /v1/businesses/{business_id}/bank/transactions`. `contracts/openapi.json` and `frontend/lib/api/schema.d.ts` are regenerated. No web code calls it yet |
| sign convention | the fixture's Plaid fake turns our-sign cents back into Plaid's convention (positive is money out) so that `_values` stays the only place a Plaid amount is flipped for storage. The flip back lives only in the fake and is documented there |
| nightly job | a database with the sample loaded holds 2 connections whose access token is a placeholder. A local `run_due` would try them against Plaid, fail, and count failed nights (AD-051). The sample is not meant for a database where the nightly job runs |
| stored data | nothing to migrate. No schema change |

## Relations

`None - no stored-data shape change`. The loader creates ordinary rows (1 user, 1 business, 1 membership, 2 connections, 4 accounts, the transactions, audit entries) through the existing services.

## Surface

| Route | In | Out | Status |
| --- | --- | --- | --- |
| `GET /v1/businesses/{business_id}/bank/transactions` | query `limit` (1-500, default 100), `cursor` (opaque, optional) | `items[]` of `Transaction` (`id`, `account_id`, `date`, `amount_cents`, `currency`, `pending`, `description`, `counterparty`, `label`) · `next_cursor` (string or null) | `200`, `403`, `404`, `422` |

The loader command is not an HTTP route: `python -m app.fixtures.load <fixture>` takes `harbor_street`, `--seed` (int, default 0) and `--clerk-user-id` (default `user_sample_harbor_street`). It prints the business ID on stdout, or one error line on stderr, and exits `0` (loaded, or already loaded), `1` (refused or failed) or `2` (usage).

## Landing

| One-way door | Literal shape | Alternative rejected |
| --- | --- | --- |
| 1. Transactions route | `GET /v1/businesses/{business_id}/bank/transactions?limit=&cursor=`, owner only (AD-031), on the authenticated `/v1` router (AD-022). Body `{"items": [Transaction], "next_cursor": str \| null}`, newest first by `(date desc, id desc)`. `Transaction` = `id`, `account_id`, `date` (ISO date), `amount_cents` (our sign), `currency`, `pending`, `description`, `counterparty` (null), `label` (AD-057). No Plaid IDs, no category, no link. `cursor` is the URL-safe base64 of `<date>/<id>` of the last item; a cursor that doesn't decode is `422` problem details (AD-008) | Offset paging (`page=`): a sync that inserts mid-read shifts every later page and repeats or skips rows. A bare array: AD-032's lists are `{"items": ...}` so they can grow a cursor, and this one needs one now. Returning `category` and `linked_transaction_id`: no consumer yet, and each would become a contract |
| 2. Fixture data contract | `app/fixtures/harbor_street.py`: `REFERENCE_DAY = date(2026, 9, 26)`, `generate(seed: int = 0) -> SampleBusiness`, a frozen dataclass with `business` (name, province `ON`, time zone `America/Toronto`), `banks` (each with its institution and accounts: key, name, type, mask, `balance_cents`, `available_cents`), `history` (each `SampleTransaction`: stable `key`, `account_key`, `date`, `amount_cents` our sign, `currency`, `description`, `counterparty`, `category`, `category_detailed`), `expected_payments` and `future` (`opening_cents`, dated `items`, 13 `weeks` with `start` and `end_cents`). Amounts are `int` cents with `"CAD"` everywhere. Seeded with `random.Random(seed)` only | Data in a JSON or CSV file: 18 months of rows can't be read in review, and a seed is then a lie. Plaid-shaped output (`PlaidTransaction`): specs 19 and 22 would flip signs outside `bank_sync`. `numpy` random: a new dependency for a few hundred draws |
| 3. Loading through a fake Plaid | `app/fixtures/plaid.py` `FixturePlaidClient(bank)` implements `PlaidClient`: `exchange_public_token` -> item `sample-<business_id>-<bank key>` (amended 2026-10-06, approved by the user: the seed alone made a second load of the same seed break the unique Plaid IDs), `get_accounts`, `get_institution_name`, `sync_transactions` (one page, `has_more` false, cursor `sample-done`). Every other method raises `PlaidError(error_type="SAMPLE", error_code="NOT_SUPPORTED")`. Plaid IDs are `sample-...` throughout, and the access token is `sample-not-a-token`, Fernet-encrypted as usual. `load` refuses unless the `DATABASE_URL` host is `localhost`, `127.0.0.1` or `::1` | A `bank_sync.service.import_sample(...)` that inserts rows: a second write path that skips the sign flip, labels and audit the real path runs, and production code that exists only for tests. Raw SQL inserts in the loader: breaks module data ownership (AGENTS.md) |

- Recorded in `.specs/STATE.md`: door 1 AD-067, door 2 AD-068, door 3 AD-069.
- Nothing else here is hard to reverse. The descriptions, client names, amounts outside the mockups, and the transfer rule can all change in the diff.

## Criteria

Amounts are integer cents. "Week of Nov 9" means Monday 2026-11-09 to Sunday 2026-11-15. "The 13 weeks" run from Monday 2026-09-28 to Sunday 2026-12-27 (the dashboard mockup's "Forecast through December 27"). "Week end" is the balance after the week's last flow. "Owner" is AD-031's owner.

### S1: The same seed always gives the same Harbor Street Plumbing (P1)

`generate(seed)` is a pure function whose output matches the mockups.

**Acceptance Criteria**

1. WHEN `generate(seed)` is called twice with the same seed THEN the system SHALL return equal `SampleBusiness` values, and their JSON serialisations SHALL be byte-identical. (Spec 18 "Done when" 1.)
2. WHEN `generate` is called with two different seeds THEN the system SHALL return histories that differ in at least one client payment amount, and identical `banks`, `expected_payments` and `future`.
3. The sample business SHALL be named "Harbor Street Plumbing", in province `ON` and time zone `America/Toronto`.
4. The sample SHALL have exactly 2 banks: "Harbor Community Bank" with Operating checking (`checking`, mask `2381`, balance 800000), Reserve savings (`savings`, mask `9025`, balance 3430000) and Line of credit (`line_of_credit`, mask `7702`, balance 0, available 2000000); and "Summit Federal" with Business Visa (`credit_card`, mask `5530`, balance owed 245000). Every account SHALL be in `CAD`.
5. The history SHALL date every transaction from 2025-03-26 to 2026-09-26, with the earliest on or before 2025-04-01, and every amount SHALL be a non-zero `int` with currency `CAD`.
6. The history SHALL hold a payroll of -1120000 from Operating checking every 14 days, on the Fridays of the cadence that ends 2026-09-18, moved to the previous business day (AD-059) when the Friday is a holiday: 2025-04-17, 2025-12-24 and 2026-04-02.
7. The history SHALL hold, in every calendar month from April 2025 to September 2026, one rent payment and one software subscriptions payment from Operating checking, each with the same amount and day-of-month rule all 18 months.
8. The history SHALL hold Coastal Supply Co bills in every calendar month from April 2025 to September 2026, and client payments from at least 4 named clients including "Acme Co" and "Birch & Co".
9. The history SHALL hold Business Visa purchases, and in every calendar month a payment from Operating checking to the card, both halves the same amount at most 3 business days apart.
10. The history SHALL hold at least one transfer between Operating checking and Reserve savings in every calendar month, both halves the same amount on the same day.
11. WHEN the balances are rebuilt backward from the reference-day balances THEN, for every seed from 0 to 9, no end of day from 2025-03-26 to 2026-09-26 SHALL leave Operating checking or Reserve savings below 0, or the Business Visa owing less than 0.

**Independent test:** `uv run pytest tests/test_fixture_harbor_street.py`.

### S2: The sample holds the cash gap from the alert mockup (P1)

The reference future and the expected payments carry the Nov 9 gap, so that specs 21 to 25 have one target.

**Acceptance Criteria**

12. The sample's expected payments SHALL be exactly the 4 from the expected-payments mockup: "Acme Co, invoice 1042" +800000 on 2026-10-06, once; "Coastal Supply Co, quarterly order" -1450000 on 2026-11-12, every 3 months; "Birch & Co, invoice 1057" +960000 on 2026-11-17, once; and "Equipment lease deposit" -300000 on 2026-12-07, once. Each SHALL be on Operating checking.
13. The reference future SHALL open at 4230000 (Operating + Reserve) and SHALL have 13 weeks starting Mondays 2026-09-28 to 2026-12-21, each week's end being the opening plus every item dated up to that week's Sunday.
14. The week of Nov 9 SHALL end at 315000, and every other week SHALL end at or above 1765000.
15. The week of Nov 9 SHALL include Coastal Supply Co -1450000 on 2026-11-12 and Payroll -1120000 on 2026-11-13, and Birch & Co +960000 SHALL be dated 2026-11-17.
16. The reference future items dated 2026-09-27 to 2026-10-09 SHALL be exactly: Payroll -1120000 on 2026-10-02, Acme Co +800000 on 2026-10-06, Software subscriptions -64000 on 2026-10-07, and Business Visa payment -245000 on 2026-10-08 (the dashboard mockup's next 14 days).
17. WHEN the reference future is recomputed with Birch & Co dated 2026-11-10, or with Coastal Supply Co dated 2026-11-19, or with +200000 added on 2026-11-09 and -200000 on 2026-11-17 THEN the lowest week end SHALL be 1275000, 1765000 and 515000 respectively (the alert mockup's three fixes).
18. The reference future's payroll, rent and software items SHALL continue the history's schedules and amounts: payroll every 14 days from 2026-10-02, with 2026-12-25 moved to 2026-12-24.

**Independent test:** `uv run pytest tests/test_fixture_harbor_street.py -k future`.

### S3: One command loads the sample into the local database (P1)

**Acceptance Criteria**

19. WHEN `python -m app.fixtures.load harbor_street` runs against an empty local database THEN it SHALL exit 0, print the new business ID, and leave the business owned by the user with Clerk ID `user_sample_harbor_street` (or `--clerk-user-id`).
20. WHEN the load has finished THEN `GET .../bank/connections` as the owner SHALL return the 2 banks and 4 accounts of AC 4. Operating checking and Reserve savings SHALL have `included` true, Operating checking SHALL be `primary`, each connection's `status` SHALL be `synced`, and `last_synced_at` SHALL be `2026-09-26T10:02:00Z`. (Spec 18 "Done when" 2, accounts.)
21. WHEN the load has finished THEN following `next_cursor` through `GET .../bank/transactions` SHALL return every history transaction of the same seed exactly once, with the same date, `amount_cents` (our sign), currency and description. (Spec 18 "Done when" 2, transactions.)
22. WHEN the load has finished THEN both halves of every Operating/Reserve transfer SHALL be labelled `internal_transfer`, both halves of every card payment `card_payment`, and no transaction SHALL be `in_transit`.
23. WHEN the load commits a bank's sync THEN the system SHALL publish one `transactions.synced` for that connection, with `added` equal to that bank's history count, to the handlers registered by `subscriptions.register()`.
24. WHEN the load runs again for an owner who already owns the fully loaded sample (2 connections) THEN it SHALL exit 0, print "already loaded" with the business ID, and change no row.
25. IF the owner already owns a business that is not the fully loaded sample THEN the load SHALL exit 1 with one stderr line naming the business ID, and write nothing.
26. IF the `DATABASE_URL` host is not `localhost`, `127.0.0.1` or `::1` THEN the load SHALL exit 1 with "Refusing to load sample data into a non-local database." and connect to nothing.
27. IF the fixture name is not `harbor_street` THEN the command SHALL exit 2 with argparse's usage error listing `harbor_street`.
28. WHEN a load finishes THEN it SHALL log one `fixture.loaded` line with `fixture`, `seed`, `business_id` and `transactions`, and SHALL log no access token.

**Independent test:** in pytest, run the loader's `main` against the test database, then call both routes with an owner token.

### S4: The owner reads transactions through the API (P1)

**Acceptance Criteria**

29. WHEN the owner calls `GET .../bank/transactions` THEN the system SHALL answer `200` with `items` ordered by date, newest first, then by `id` descending, at most `limit` items (default 100), and `next_cursor` set when more remain.
30. WHEN the last page is returned THEN `next_cursor` SHALL be null, and following every cursor from the first page SHALL visit each of the business's transactions exactly once.
31. IF the business has no transactions THEN the system SHALL answer `200` with `{"items": [], "next_cursor": null}`.
32. IF `limit` is below 1 or above 500, or `cursor` does not decode to a date and an ID, THEN the system SHALL answer `422` problem details (AD-008).
33. IF the caller is not a member of the business THEN the system SHALL answer `404` "Business not found.", and IF the caller's role is not `owner` THEN `403`. A transaction of another business SHALL never appear in the response.
34. The response SHALL contain no Plaid ID (`plaid_transaction_id`, `plaid_account_id`, `plaid_item_id`).

**Independent test:** `uv run pytest tests/test_bank_transactions_api.py`.

## Out of scope

| Excluded | Why |
| --- | --- |
| Loading the expected payments into a table | The table arrives with spec 20; spec 20 loads `expected_payments` from this fixture |
| A web screen listing transactions | No spec asks for one; the route is for API access |
| Loading the sample into staging or production | AGENTS.md: synthetic data for tests and demos locally; door 3 refuses non-local hosts |
| A minimum balance for the sample ($5,000) | The setting arrives with spec 23, which stores it |
| An "unload" or reset command | `docker compose` and a fresh database already do it; nothing asks for it |
| Per-account shortfall data (Operating overdrawn Oct 2) | `specs/later/`; the future is still consistent with it (AC 16) |
